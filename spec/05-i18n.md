# 05 — i18n

Two layers, one language model.

## 1. UI strings — trans tags → po files

Every short, hardcoded string in a template gets a trans tag so
skeleton-i18n can build `.po` catalogs. Use the single-line form (as in
`_block/footer.twig`): `{% trans 'string' %}` for standalone output, and
`{{ 'string'|trans }}` when the string sits inside an expression (e.g. the
masthead `default()` fallback). Both forms are picked up by the extractor.
Strings created by JavaScript get passed through templates as data
attributes instead of being hardcoded in JS (`data-format-title` on the
CodeMirror textareas → the injected Format button), since the extractor does
not scan JS files.

The source strings in the templates are the site's own wordings — currently
French for the public chrome, English for the footer's 'Non-profit
organisation' / 'Company number'. The catalogs translate from those msgids;
an empty `msgstr` falls back to the msgid, so tagging a string never changes
what visitors see until a translation is filled in. Admin sticky messages and
help texts render via trans tags in the admin templates and land in the same
catalog.

## 2. Content strings — DB (`block_translation`)

Block bodies are user-editable rich text, which should NOT go through po.
They live in `block_translation` keyed by `block_id` + `language_id`, seeded by
the block seed migration with the FR/NL/EN textual content pulled from
`../redan/{,nl/,en/}index.html`.

Rules:

- DB content is the source of truth for seeded pages; trans tags cover only
  static chrome (layout strings, form labels).
- Fallback: when no `block_translation` exists for the requested language,
  fall back to FR. This logic lives in `Block::get_translation($language)`
  (or equivalent), not in Twig.

## 3. Language selection

- `$_SESSION['language']` (default `fr`), set via `Module` event bootstrap like
  vvsjongeren's `\Language::set($_SESSION['language'])`.
- The FR/NL/EN language switcher from `../redan` stays part of the navbar
  layout, visible on every page. It posts `language` + `url` to `/lang/switch`
  (`App\Front\Module\Lang`, `login_required = false`). The redirect target is
  restricted to relative URLs (leading `/`, not `//`).
- `$_SESSION['language']` stores the **`Language` object**, not an id or
  short name: that is what `Skeleton\Application\Web::detect_language()` writes
  and what `\Language::set()` expects. `Lang` therefore assigns the object.
  (Bug caught during the build: the first version assigned `$language->id`,
  which would have broken `\Language::set()` on the next request.)

[Decision 2026-09-23] Language-prefixed URLs. Routes now also dispatch under
`/{en,fr,nl}/...` for every public module (Index root, Login, Download,
Picture, Lang switch and the existing Forms endpoints: Members with
`calendar.ics`, Form\Calendar): see `app/front/config/routes.php`. The first
segment uses the router's variable syntax, `$language[en,fr,nl]`, so the
router fills `$_GET['language']` and the existing module bootstrap event
consumes it exactly like the `?language=xx` query-string switch — no
language-specific PHP anywhere. `/`, `/login` and friends keep working with
the session language; `/admin` and the CalDAV endpoints stay unprefixed
because they are per-language editing / protocol URLs, not visitor pages.

[Decision 2026-09-29] The routable language list has two readers, not one: the
router, and `Seo_Sitemap`, which publishes one `<url>` per language with the
full hreflang set (see 02-public-site.md, "Sitemap and robots.txt"). The
sitemap reads the `$language[...]` restriction out of the `Index` route rather
than repeating it, so the route list stays the single source of truth for
which prefixes exist. This matters here and not elsewhere because a language
added to the route list is discovered by the sitemap for free, while a
language row that is in the database but *not* in the route list is not
dispatchable and must not be published — publishing it would put a 404 in the
sitemap.

hreflang is published in the sitemap only. The page head is the other
supported place for it (`<link rel="alternate" hreflang="..." href="...">`,
which Google documents as the primary method) and is **not** emitted: it would
need the absolute per-language URLs assigned from `Module` bootstrap into every
layout, and with three languages and one page the sitemap set is complete on
its own. Adding the head links later is additive, not a correction; if both
ever exist, they must agree, so both should read the same source.


## 4. Generate command

```bash
util/bin/skeleton i18n:generate
```

One translator per application, named after the app (`front`); its extractor
scans the whole `app/front/template/` directory and its Po storage writes
`po/<language name_short>/front.po`. There is no separate extract/compile
stage: `Storage\Po` reads the `.po` files directly at runtime (no `.mo`).
Each run adds new msgids and deletes stale ones for every language.

[Decision 2026-09-28] The extractor scans **two** trees into the same `front`
catalog: `app/front/template/` and `store/email/template/`. The mail templates
are Twig, rendered by `Skeleton\Email\Email`, and they ship with the
`tigron/skeleton-email` package; leaving them out of the scan meant the
generator would drop every mail msgid as stale on its next run. Done with
`I18n_Extractor_Multiple` (`lib/component/I18n/Extractor/Multiple.php`, returns
the merged, de-duplicated string list of the extractors it wraps) plus an
`App\Front\Event\I18n` event that sets the twig paths. One catalog, one
extractor, no second translator to keep in sync.

Reset mail, added with it: `store/email/template/password_reset/{subject,html,text}.twig`
(all three are required by skeleton-email). The mail is written in the
**recipient's** language, not the admin's: `Password_Reset_Mail::send()` resolves
`user.language_id` and falls back to `Language::get_default()` when it is
unset or points at a deleted language, then hands that catalog to
`Email::set_translation()`. The same resolution is used by the admin list column
for the language name.

Mail transport is optional configuration, all in the gitignored
`config/environment.php` (never `app/front/config/environment.php`, which holds
the hostnames and the default language):

- `email_transport` — `smtp` to use SMTP, anything else/absent for sendmail.
- `email_smtp` — `[ 'host' => …, 'port' => …, 'encryption' => …,
  'username' => …, 'password' => … ]`, only read when the transport is `smtp`.
- `email_sendmail_command` — optional sendmail binary path, otherwise the
  `sendmail` found in `PATH`.

The sender address is the `contact_email` setting (not a config key), with
`masthead_title` as the sender name and `GS Redan` as the fallback. Nothing in
the mail path logs a token, and the raw token is only ever in the link itself.

New strings from the grouped admin menu (2026-09-28): `Content` and
`Administration`, the two group headings in `menu.admin.twig`. Short nouns, no
translation hazard, and they were chosen so the grouping is self-explanatory
without a caption.

New strings from the self-service reset form on the login screen (2026-09-28),
all untagged-but-present in `login.twig` and waiting for the generator like the
rest: `Forgot your password?`, `Send reset link`, `Back to log in`, the form
hint ("We mail a link that lets you choose a new password. For your security it
is the same answer whether or not the address is known here."), and the neutral
confirmation `If that address belongs to an admin account, a reset link is on
its way. It is valid once, for 24 hours.`. The last one is deliberately
address-agnostic: it must stay readable as *the* answer for every address, so
it is never split into a success and a failure variant, and the wording may
not grow into something that implies a lookup result.

Catalog workflow: the new admin/user and reset strings were **not** added to
`po/*/front.po` by hand. `util/bin/skeleton i18n:generate` needs a database
connection and the CLI PHP here has no `ext-mysqli`, and the fr/nl msgstr are
meant to come from the translation service (DeepL/TAS) rather than from me
guessing. Run the generator and the translation service where the extension is
available, then fill `msgstr` in `po/fr/front.po` and `po/nl/front.po`.
