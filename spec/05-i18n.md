# 05 — i18n

Two layers, one language model.

## 1. UI strings — trans tags → po files

Every short, hardcoded string in PHP or Twig navigation gets a trans tag so
skeleton-i18n can build `.po` files. This includes:

- Twig templates: every nav title, form label, button, sticky message, empty
  state, validation error text. Use the skeleton twing extension form, e.g.
  `{% trans %}Bookings{% endtrans %}` / `{{ 'Save'|trans }}`.
- PHP code: sticky messages and exception strings go through
  `Skeleton\I18n\Translator` so the extractor can find them.
- Tailored for the extractor (`util/bin/skeleton translate:extract` —
  confirm the exact console command in skeleton-i18n when implementing).

Translations land in the po files for `fr`, `nl`, `en` (languages seeded in the
`language` table; FR is default+fallback). Every trans string present in the
source must get a translation for all three languages as part of the work —
prefill them (English strings are from the current site's own wordings, use the
`../redan/en/index.html` wordings where a string logically matches).

## 2. Content strings — DB (`block_translation`)

Block bodies are user-editable rich text, which should NOT go through po.
They live in `block_translation` keyed by `block_id` + `language_id`, seeded by
the block seed migration with the FR/NL/EN textual content pulled from
`../redan/{,nl/,en/}index.html`.

Rules:

- DB content is the source of truth for seeded pages; trans tags cover only
  static chrome (layout strings, form labels).
- Fallback: when no `block_translation` exists for the requested language,
  fall back to FR. This logic lives in `Block::get_translation($language)`
  (or equivalent), not in Twig.
- The i18n template extension must be enabled for markdown/rich HTML output in
  templates, per `skeleton-i18n` `Template\Twig` utilities (see the existing
  `macro.base.twig` usage).

## 3. Language selection

- `$_SESSION['language']` (default `fr`), set via `Module` event bootstrap like
  vvsjongeren's `\Language::set($_SESSION['language'])`.
- The FR/NL/EN language switcher from `../redan` stays part of the navbar
  layout, visible on every page. It posts `language` + `url` to `/lang/switch`
  (`App\Front\Module\Lang`, `login_required = false`). The redirect target is
  restricted to relative URLs (leading `/`, not `//`).
- `$_SESSION['language']` stores the **`Language` object**, not an id or
  short name: that is what `Skeleton\Application\Web::detect_language()` writes
  and what `\Language::set()` expects. `Lang` therefore assigns the object.
  (Bug caught during the build: the first version assigned `$language->id`,
  which would have broken `\Language::set()` on the next request.)


## 4. Extract + build command

Confirm the skeleton-i18n command names in this repo before coding; typically:

```bash
util/bin/skeleton i18n:extract   # extract trans strings to .po
util/bin/skeleton i18n:compile   # compile .po -> .mo for runtime
```

(Exact names come from `lib/external/packages/tigron/skeleton-i18n/console/`.)
